## 2. Posting text (key responsibilities and qualifications)

Several FDE variants are posted: plain FDE, Applied AI, Custom Agents, Federal Civilian, Staff, and Manager/Head of FDE. Requirements differ by variant. All items below are `(confirmed)` from Greenhouse snippets.

**Responsibilities**
- Embed with strategic customers to drive AI adoption, and provide hands-on, "white glove" deployment support for Anthropic products in customer environments [S7][S10].
- Build production applications with Claude models inside customer systems [S8].
- Deliver technical artifacts such as **MCP servers, sub-agents, and agent skills** that go into production workflows [S8].
- Build long-term customer relationships and find new deployment opportunities [S7].
- Staff level: lead the technical direction of the customer's AI adoption, "operate autonomously, thrive under ambiguity, and represent Anthropic at the highest level in customer environments" [S9].
- Federal variant: wants production LLM experience, including agent development and **evaluation frameworks** [S10].

**Qualifications**
- 4+ years in a technical, customer-facing role, or software engineering with consulting/product experience [S7][S8]. One variant asks for 8+ years plus **25–50% travel** to customer sites [S11]. Some versions say 3+ years [S12].
- Strong Python. TypeScript or Java is a plus. Experience shipping production applications [S8].
- High agency in ambiguous enterprise organizations [S7]. Former technical founders are encouraged to apply [S7].
- Bachelor's degree or equivalent experience. Candidates are encouraged to apply even without every qualification [S7].
- Pay varies by listing: about $200K–$300K in some, $280K–$400K for the Custom Agents posting (SF/NYC), and £225K–£255K in London [S8], per snippet summaries.

**Candidate fit:** your profile matches several of these points directly. You have 10+ years of technical customer-facing work, and your solo platform covers what S8 names: MCP server, sub-agents/research agents, and production workflows with approvals and audit logs. The evals point in S10 is the gap to close.

## 3. Interview stages (in order)

Anthropic does **not** publish an FDE-specific loop [S14] `(reported)`. Guides disagree on the round count: 5 stages [S13]; recruiter → technical use-case → coding → HM → final panel [S15]; and "7–8 rounds" in another DataInterview table [S14]. Reported timeline: about 4–6 weeks, with technical and values rounds often bundled into a 4–5 hour virtual onsite [S14][S15] `(reported)`. Confirmed general facts: all interviews run on Google Meet, technical candidates do live coding in tools like **Colab and CodeSignal**, and candidates **may look up syntax and libraries** [S2] `(confirmed)`.

### Stage 1: Recruiter screen
- **Tests:** background, motivation, "Why Anthropic / why FDE" [S13][S28] `(reported)`.
- **Reported questions:** "Which of our models have you used, and what did you build?" and "Why Forward Deployed Engineer?" [S15][S16] `(reported)`.
- **Method:** a 60-second pitch: customer-facing engineer → built a production Claude platform solo → wants to do that for strategic customers. Name one specific Anthropic artifact you have read (RSP v3.x, Core Views) and say what you think of it.

### Stage 2 (sometimes): Online coding assessment (CodeSignal, progressive)
- **Tests:** writing clean, extensible code fast. One problem runs across **4 levels** (some candidates report 6), each extending the last, so early design choices matter. About 60–90 minutes [S17][S18] `(reported)`.
- **Reported problems:** an in-memory key-value DB (most reported), a bank with transaction types, a file system, a package manager [S17][S18]. In-memory DB levels reportedly add filtered scans, TTL with timestamps, then compression or persistence to file [S19][S17]. A bank system adds balances, scheduled transactions, and interest [S26]. A Sept 2026 Reddit report describes a 4-level in-memory **banking** system: a score of 580 led to rejection, while another candidate advanced with 580 [S18] `(reported)`.
- **Caveat:** these reports come mainly from SWE candidates. Whether FDE candidates always get this assessment is not established.

### Stage 3: Technical screen / live coding (practical, incrementally extended)
- **Tests:** practical Python or TypeScript, not LeetCode-hard. Constraints are added step by step, "like real customers" [S13][S16] `(reported)`.
- **Reported questions:**
  - Implement an **LRU cache**, then extend it as constraints are added [S16][S24] `(reported, FDE-tagged)`. SWE reports describe the extension path: fix a bug in a given Python LRU (the key built from `*args/**kwargs`), then "how would you make it persistent?" [S20][S21] `(reported, SWE)`.
  - **Rate limiter**, with deep follow-ups on distributed coordination [S15] `(reported)`.
  - Process call stacks into execution traces [S15] `(reported)`.
  - LLM-adjacent scenarios: a token-budget allocator, a tool-use orchestrator, a rate limiter [S13] `(reported)`.
  - **Web crawler**, single-threaded then concurrent, with a thread-safe visited set and queue [S22][S23] `(reported, SWE; S23 dated Oct 2025)`.
- **Method (to cover your weak spot):** clarify → examples → plan → code → test → extend.
  1. **Clarify** inputs, outputs, edge cases, and scale out loud (about 2 minutes).
  2. **Examples:** write 2–3 concrete input/output cases as asserts first.
  3. **Plan for extension:** pick a small class with clear methods and a dict-based state. Avoid clever one-liners, because the next level will force a refactor.
  4. **Code** the simplest correct version. Narrate as you go.
  5. **Test:** run the asserts and add edge cases (empty input, duplicates, TTL boundary).
  6. **Extend and optimize** at each new level: refactor before adding features, and keep earlier tests passing.
  - Drill these until automatic: `collections.OrderedDict` / `deque` / `defaultdict` / `heapq`, `threading.Lock`, `concurrent.futures`, `dataclasses`, and `time.monotonic()`. Looking up syntax is allowed in live rounds [S2], so practice fluent lookup without AI help.

### Stage 4: Technical use-case / Claude deployment scenario
- **Tests:** deployment reasoning and **MCP fluency**. One guide describes a live scenario with Claude and MCP tools, not a take-home [S15] `(reported)`. There is also an MCP design task with explicit **trust boundaries** [S15][S16] `(reported)`.
- **Reported question:** compare hosted (API) and self-hosted (open-weights on customer infrastructure) deployments for an enterprise customer [S15] `(reported)`.
- **Method:** state the goal and success metric → data sources and their sensitivity → tool and MCP surface with least privilege → human approval points → logging and audit → evals and rollout. Your own approval steps and audit logs make a strong worked example.

### Stage 5: Customer-conversation simulation / role-play
- **Format:** live role-play with no editor. Anthropic engineers play non-technical executives or skeptical enterprise architects. You run discovery on business constraints, data-privacy boundaries, and past AI failures [S13][S16] `(reported)`. Several guides call it the decisive round that cuts the most candidates who passed coding, but none cite a primary source [S13][S16] `(reported)`.
- **Reported opener:** an executive says they want to "put Claude on their internal knowledge base." The guide's advice is to resist designing and ask discovery questions first [S13] `(reported)`.
- **Method (discovery-call structure):**
  1. **Agenda and roles** (30 seconds).
  2. **Business goal:** what changes if this works, who uses it, and how success is measured.
  3. **Current state:** workflow, systems, data location and owners, volume.
  4. **Constraints:** privacy and compliance, residency, security review, budget, timeline.
  5. **History:** what AI efforts were tried before and why they failed.
  6. **Risks and stakeholders:** who can block it, and what a failure looks like.
  7. **Play back** a summary → propose a **narrow pilot** with an eval set → agree next steps.
  - Push back with reasons and translate tradeoffs into the customer's terms [S13] `(reported)`. Your years of equipment customer work count here: use real stories about scoping, managing expectations, and handling a skeptical buyer.

### Stage 6: System design (Claude deployment design)
- **Tests:** architecting a Claude deployment for a specific enterprise customer [S13] `(reported)`.
- **Method:** requirements (functional, non-functional, compliance) → high-level architecture (ingest/RAG, orchestration, tools/MCP, model choice, batch vs. real-time) → data flow and trust boundaries → failure modes (hallucination, prompt injection, rate limits, cost) → **evaluation** (golden set, LLM-as-judge with human calibration, regression tests on prompt changes) → observability and audit → rollout (pilot, then expand).

### Stage 7: Hiring manager / project deep dive
- **Tests:** ownership and depth on a past project [S15] `(reported)`. DataInterview has a dedicated "project deep dive" module [S14] `(reported)`.
- **Method:** walk through your AI platform as STAR plus architecture: problem → constraints → design decisions and tradeoffs → what broke → metrics → what you would change (for example, "I'd add formal evals earlier").

### Stage 8: Values / culture interview
- **Tests:** mission alignment, AI-risk reasoning, honesty. Reportedly weighted equally with technical rounds and run by a non-technical interviewer [S13][S15] `(reported)`.
- **Reported questions:** "Tell me about a time your values were tested at work" and "What worries you about deploying powerful AI?" [S15][S16] `(reported)`.
- **Method:** STAR stories with an honest reflection at the end. See sections 5 and 6.

## 4. Anthropic AI guidance for candidates `(confirmed)` [S1]

Last updated 2025-07-10. Stage by stage:
- **Application:** "Please create your first draft yourself, then use Claude to refine it." The experience described must be yours.
- **Take-home assessments:** "Complete these without Claude unless we indicate otherwise."
- **Interview prep:** encouraged. "Use Claude to research Anthropic, practice your answers, and prepare questions for us."
- **Live interviews:** "This is all you–no AI assistance unless we indicate otherwise." Request accommodations from your recruiter early.
- **Not OK:** using Claude to invent experiences, or having Claude write code in an assessment without explicit permission.
- Context `(reported)`: this replaced an earlier stance of "please do not use AI assistants during the application process," and Fortune covered the reversal on 2025-07-21 [S25].
- Also `(confirmed)` [S2]: recruiters contact candidates only from @anthropic.com addresses.

## 5. Responsible Scaling Policy and Core Views `(confirmed)`

**RSP** [S4][S5]
- **Current version: 3.4, effective 2026-07-08.** The page was updated 2026-08-14. **v3.0 (effective 2026-02-24) was "a comprehensive rewrite."** Later versions: 3.1 (2026-04-02), 3.2 (2026-04-29), 3.3 (2026-05-26), 3.4 (2026-07-08).
- v3.x elements: **Frontier Safety Roadmaps** with detailed safety goals, and **Risk Reports** that "quantify risk across all our deployed models" (published Feb 2026 and Aug 2026). The **Long-Term Benefit Trust** can request external review of Risk Reports (v3.2). There is a Noncompliance Reporting and Anti-Retaliation Policy (updated 2026-03-24). Anthropic keeps the freedom to pause development even when the RSP does not require it (v3.1).
- **Capability thresholds** cover CBRN (revised in v3.3) and AI R&D, including automating entry-level AI research and dramatically accelerating effective scaling. The automated-R&D threshold was revised in v3.4. Anthropic determined that **Claude Opus 4.6 does not cross AI R&D-4** (2026-02-10). Crossing AI R&D-4 would require an affirmative case on misalignment risk.
- **ASL levels:** the overview page treats **ASL-2** as the baseline. The **ASL-3 Deployment Standard** is four-layer defense in depth: access controls, real-time prompt/completion classifiers, asynchronous monitoring, and jailbreak detection with rapid response, focused on CBRN misuse. The **ASL-3 Security Standard** includes multi-party authorization for weight access, binary authorization, supply-chain security, honeypots, and red teaming. The page does not define ASL-4+; read the PDF [S5] for formal definitions.
- **FDE angle:** customers will ask about classifiers and usage policies. Be ready to explain why safeguards exist and how they affect deployments.

**Core Views on AI Safety** (2023-03-08) [S6]
- AI may progress rapidly: the essay puts a ">10% likelihood" on broadly human-level AI within a decade. Safety is unsolved, and some risks appear only at the frontier, so Anthropic says it is "necessary to do safety research on 'frontier' AI systems."
- **Scenarios:** optimistic (existing methods like RLHF and Constitutional AI mostly suffice), intermediate (solvable with substantial work), pessimistic (unsolvable; then "sound the alarm" and don't build).
- **Research portfolio:** capabilities (largely unpublished), alignment capabilities (RLHF, Constitutional AI), alignment science (interpretability, red-teaming).
- **Empirical approach:** "show, don't tell" and "planning is indispensable, but plans are useless."

## 6. Values and culture themes

**Official values** `(confirmed)` [S3]: Act for the global good · Hold light and shade · Be good to our users · Ignite a race to the top on safety · Do the simple thing that works · Be helpful, honest, and harmless · Put the mission first. Anthropic calls itself "a high-trust, low-ego organization" [S2][S3]. It says: "We care about what you can do, not where you learned to do it" [S2].

**Reported interview themes** `(reported)` [S28][S29][S30]. Search summaries did not attribute each line to one site, so treat these as a group.
- "Why Anthropic" needs specifics. Generic safety answers reportedly fail, so cite research you have engaged with and hold a view on.
- Intellectual honesty: calibrated uncertainty, saying "I don't know," and willingness to push back, even on Anthropic.
- **Performing alignment is penalized.** Enthusiasm or signaling without substance is reported as a top disqualifier.
- Long-term thinking, humility, low ego, direct communication.
- **Candidate angle:** "Do the simple thing that works" maps to your solo platform, which uses n8n and Supabase rather than over-engineering. "Be helpful, honest, harmless" maps to your approval steps and audit logs. Prepare an honest story about a time you told a customer "no" or delivered bad news about equipment limits.

## 7. Gaps and caveats
- **Network limits:** job-boards.greenhouse.io and all third-party sites failed to resolve in this session, so posting text and third-party claims come from search snippets and summaries. Before the interview, read the exact posting you applied to in full.
- **No official FDE loop:** stage order and count are a composite. Ask your recruiter: (a) is there a CodeSignal OA for FDE? (b) Python or TypeScript? (c) is there a role-play round? (d) is any AI use permitted in any round?
- **Progressive coding:** confirmed for the CodeSignal OA only through SWE-heavy reports [S17][S18]. An LRU cache appears on FDE question lists [S16][S24], but its staged extensions come from SWE reports [S20][S21]. The web crawler is SWE-only [S22][S23]. Score thresholds such as "520+" or "580" are anecdotal and inconsistent.
- **"Decisive role-play round"** and "values weighted equally" are repeated across guides without primary sourcing.
- **Job titles:** S27 claims Anthropic uses "Applied AI Engineer" for this work instead of FDE (low-verification site). Greenhouse shows both "Forward Deployed Engineer" and "…, Applied AI" titles.
- **RSP ASL definitions** were not read from the PDF. ASL-3 activation date and ASL-4 details are unverified here.
- Glassdoor data covers all Anthropic roles (about 36% positive experience, difficulty 3.36/5) and is not FDE-specific [S31].

## Illustrative practice questions (not reported; written for practice only)
1. Implement a `KVStore` with `set/get/delete`. Level 2: `scan(prefix)`. Level 3: TTL with timestamps. Level 4: `backup()/restore(ts)`.
2. A customer's Claude agent occasionally emails the wrong supplier. Walk through discovery, root cause, and the guardrails you would add.
3. Design an eval suite for a research agent that uses web search and writes reports. What do you measure, and how do you catch regressions?
4. A manufacturing customer wants Claude on its service-ticket history with no data leaving its VPC. Compare options and recommend one.
5. Tell me about a time you shipped something solo that failed in production. What did you change?
6. What part of the RSP do you disagree with or find hardest to explain to a customer?
